# Дизайн развития llmtuner

Решения согласуются с владельцем по одному, до начала реализации. Каждый пункт
реализуется только после того, как его детали записаны здесь.

## Общие решения (2026-11-21)

- **Роль.** llmtuner — общий инструмент для любых проектов владельца. Ядро ничего не знает
  о предметной области; всё специфичное (цели, проверки, словари) живёт в самих проектах,
  как `scripts/llmtuner_*.py` в hiphop-discovery.
- **Метки человека** привязываются к паре «кейс + ответ», а не к прогону. Метка действует
  везде, где на тот же кейс снова пришёл тот же ответ; новый ответ виден как «не размечено».
- **Источник правды** для датасетов и меток — файлы в проекте (личные — в папке вне git,
  как `artifacts/` в hiphop-discovery). База llmtuner хранит только историю прогонов;
  метки, поставленные на странице, записываются обратно в файл проекта.
- **Порядок реализации** — от фундамента: 6 инфраструктура → 3 защита от подгонки →
  1 метки и качество → 4 данные → 2 дизайн страницы → 5 многошаговые агенты и трассы.

## 6. Инфраструктура (согласовано 2026-11-21)

- **Установка:** `uv tool install --editable ~/Projects/LLMtuner` с дополнением `mcp`.
  Команда `llmtuner` доступна везде, правки кода подхватываются сразу. MCP-сервер у агентов
  регистрируется как `llmtuner mcp` (регистрацию в hiphop-discovery перевести на неё).
- **GitHub:** приватный репозиторий под аккаунтом `NUKI1223`. Создание репозитория и каждый
  push — только с согласия владельца на этот шаг.
- **Проверка версий Python:** 3.12 (минимальная заявленная) и самая новая в системе;
  набор тестов с пакетом `mcp` и без него.
- **Автоматические тесты:** GitHub Actions на приватном репозитории, на каждый push.
- **Claude Code и mise:** системные настройки не трогаем. llmtuner, его скрипты и тесты
  никогда не вызывают команду `claude` (её вызов через mise обновляет Claude Code).

## 3. Защита от подгонки (согласовано 2026-11-21)

- **Журнал правок** эталонов — файл рядом с датасетом (`<датасет>.changes.jsonl`): кто, когда,
  зачем, что было до. Правки делаются командой `llmtuner case edit` и инструментом MCP,
  которые пишут запись сами; правка в обход них помечается как «не записана».
- **Причина обязательна** для каждой правки эталона test-части — и у человека, и у агента;
  агент должен ссылаться на правило или пожелание владельца, а не на ответ модели.
- **Holdout через MCP:** агент может запускать не чаще раза в сутки на проект и датасет;
  человек из командной строки — без ограничений.
- **Деление на части** — вручную, полем `split` в файле; `llmtuner split` может предложить
  случайное деление, но ничего не меняет без владельца.

- **Изменённая test-часть:** прогон не блокируется, но отчёт крупно показывает test-кейсы,
  изменённые после предыдущего прогона; `compare` и `gate` помечают их как несравнимые.
- **Правки эталонов агентом:** разрешены, но каждая помечается как сделанная агентом и видна
  в отчёте.
- **Скрытая часть `holdout`:** третья часть датасета помимо `dev` и `test`. Через MCP по ней
  видна только итоговая цифра — без входов, ответов и причин провала.

## 1. Метки и оценка качества (согласовано 2026-11-21)

- **Метки 11 ноября** применяются к `rage-compatible` с пометкой «из другого запроса»
  (тот же набор фильтров, другой многошаговый чат); владелец может подтвердить их для
  этого кейса на странице разметки одним нажатием.
- **Платный путь** «сообщение → помощник → подборка» оценивается отдельной целью рядом с
  бесплатной (только ранжировщик); сравнение показывает, где теряется качество. Каждый
  платный прогон — с согласия владельца.
- **Стоимость судьи** — отдельной строкой рядом с расходом проверяемой системы, плюс сумма;
  цена за правильный ответ считается только по системе.

- **«Тот же ответ»:** по умолчанию — точно такой же текст ответа; проект может указать
  в `llmtuner.toml` поле JSON-ответа (для подборок — `release_id`), и метка следует за ним.
- **Что размечает человек:** вердикт «подходит / не подходит / не знаю»; при «не подходит» —
  какие критерии запроса нарушены (из списка критериев кейса) и заметка.
- **Судья:** его вердикты считаются только после ≥ 20 меток владельца по критерию и согласия
  с ним не ниже kappa 0,6; до того — справочно, в цифру не входят. У судьи есть ответ
  «не могу сказать».
- **Главная цифра:** доля подходящих среди размеченных владельцем (с интервалом) и рядом
  покрытие — сколько ответов размечено из всех. Автоматические правила — отдельной строкой
  «нарушений правил».

### Дефекты поальбомной оценки hiphop-discovery (проверка 2026-11-21), чинить в пункте 1

1. Цель грузит каталог через `load_catalog`, сайт — через `load_with_listeners`
   (`web/app.py:57`, данные ListenBrainz). Все три подборки отличаются от сайта.
2. Заголовок «100% (15 из 15)» прячет 2 альбома, которые владелец отверг; `show --failed`
   пуст; страница не отличает «не размечено» от «не подходит» в списке.
3. Правило «нет неподходящих исполнителей» (из `grade_case`) пропускает совместные релизы
   («Drake & Future», «JPEGMAFIA & Danny Brown»); не проверяется `cards_in_scope`;
   правило жанра берётся из `expected` датасета, а не из кейса.
4. Метки 11 ноября сопоставлены с `rage-compatible` по совпадению фильтров, но поставлены
   в другом, многошаговом чате с другим текстом запроса.
5. Тесты не проходят настоящий путь подборки (заглушка), подмены каталога и сидов не ловятся.
6. Сбой `handle_message` выдаётся как `NO_CARD_AT_SLOT`.

## 4. Данные (согласовано 2026-11-21)

- **Ввод кейсов:** форма «Новый кейс» на странице llmtuner (запрос, контекст, критерии
  «обязательно / нельзя / желательно», примеры), запись сразу в файл датасета проекта;
  плюс команда `llmtuner case add` для агентов и скриптов (с журналом из пункта 3).
- **Кейсы из настоящих чатов hiphop-discovery:** команда проекта на основе существующего
  `src/discovery/evals/calibration.py` читает базу аккаунта только на чтение и предлагает
  кандидатов; в датасет попадает только подтверждённое владельцем. Всё личное — в
  `artifacts/`, вне git.
- **Критерии** хранятся списком в самом кейсе: у каждого id, тип (обязательно / нельзя /
  желательно), текст и цитата слов владельца. Общие критерии (не больше 2 широко известных
  из 5) задаются на уровне датасета. Разметка и судья ссылаются на id критерия.

## 2. Дизайн страницы (согласовано 2026-11-21)

- **Характер:** рабочий инструмент — спокойный, плотный, табличный, как инструменты
  аналитики; цифры и интервалы в центре, одна выразительная деталь. Проход скиллами
  `unslop` (ремесло, своя индивидуальность) и `ui-ux-pro-max` (доступность, раскладка).
- **Новые экраны (все четыре):**
  - история качества — график главной цифры по прогонам с интервалами и отметками
    изменений промпта и датасета;
  - редактор датасета — «Новый кейс», правка критериев и частей dev/test/holdout,
    журнал правок;
  - разметка с критериями — вердикт + отметки нарушенных критериев, подтверждение
    перенесённых меток одним нажатием;
  - обзор проектов — все проекты, последний прогон, сколько не размечено, расход за неделю.
- **Тема:** следовать системе (светлая и тёмная), с переключателем на странице.

## 5. Многошаговые агенты и трассы (согласовано 2026-11-21)

- **Диалоги:** сначала сценарии — кейс задаёт список реплик человека, цель получает историю
  и отвечает на каждую, проверки и метки можно ставить на любой шаг. Затем как дополнение
  симуляция пользователя моделью по описанию цели (как в τ-bench), с оговоркой, что судья
  таких диалогов часто ошибается.
- **Трассы:** простой JSONL-формат событий (вызов модели, вызов инструмента, стоимость,
  время), который приложение пишет в файл или отправляет на локальный адрес llmtuner;
  только стандартная библиотека. В hiphop-discovery источник — уже существующие
  метаданные вызовов `client.events`.
- **Живой трафик:** бесплатные кодовые проверки на каждом ответе, судья (когда проверен) —
  на выборке в пределах бюджета; график по дням. Личные данные не покидают машину.
- **Путь агента:** новые грейдеры по структуре трассы — запрещённые инструменты,
  обязательные шаги, лимит числа вызовов и стоимости, итоговое состояние.
